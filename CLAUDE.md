## Git

- Ветки: `main` (стабильная), `dev` (рабочая). Фичи — в dev, в main через merge.
- **Всё, что уходит в git и на GitHub, пишется по-английски**: сообщения коммитов (заголовок и тело), названия и описания веток, заголовки и тела PR, комментарии в PR и ревью, тексты issue, теги и release notes. Русский остаётся только в UI, в сообщениях об ошибках для пользователя и в переписке в этой сессии.
- Формат коммита прежний: `type: subject` в нижнем регистре, повелительное наклонение, без точки в конце; тело — по 72 символа в строке, объясняет «почему», а не пересказывает diff.
- Задача доведена до конца и чеклист пройден — **коммитить, не дожидаясь просьбы**. `push` — только по явному запросу: до него ветка остаётся локальной.

## Делегирование

Основная сессия не пишет всё в одиночку. Она разбирает задачу, раздаёт куски субагентам и
отвечает за то, что они вернули. Определения агентов — `.claude/agents/*.md`, общие правила
субагента (границы, формат отчёта, команды) — `.claude/agent-rules.md`.

| Агент | Модель | Для чего | Правит файлы |
| --- | --- | --- | --- |
| `typhon-go` | Sonnet | реализация и правка в `internal/*`, тесты | да |
| `typhon-frontend` | Sonnet | `frontend/src`: Svelte 5, стор, сервисы | да |
| `typhon-scout` | Haiku | разведка: где что лежит, путь вызова, факты файл:строка | нет |
| `typhon-review` | Sonnet | враждебная проверка готового дифа против инвариантов | нет |
| `typhon-verify` | Haiku | прогон чеклиста, пересборка, перезапуск | нет |
| `typhon-qa` | Sonnet | живые сценарии в настоящем окне (qa-сборка + CDP), то, что не ловится тестами | нет |

Модели подобраны под цену ошибки. Haiku — там, где нужно собрать факты или прогнать команды
и вернуть вывод дословно: он дешёвый, и его можно запускать пачкой. Sonnet — там, где пишется
код или выносится суждение (ревью, живое окно, охота на баги). Основная сессия на Opus
разбивает задачу, читает итоговый диф и принимает работу. Модель в вызове `Agent` не
переопределять без причины: она уже задана в `.claude/agents/*.md`. Haiku не отдавать ни
реализацию, ни ревью, ни приёмку — сэкономленное там уходит на переделку.

Порядок по умолчанию:

1. **Разведка.** Вопросов к коду больше одного — запускать `typhon-scout` параллельно, по одному
   вопросу на агента, все вызовы одним сообщением.
2. **Реализация.** Один агент — непересекающийся набор файлов. Двух агентов в один файл не
   пускать: их правки затирают друг друга. Не режется по файлам — режется по этапам, а не
   «как-нибудь».
3. **Проверка.** `typhon-review` и `typhon-verify` параллельно, когда правка готова и до отчёта
   пользователю. Ревью читает диф и тяжёлого не гоняет; полный чеклист — у `typhon-verify`,
   один раз и через очередь.

**Нагрузка на машину.** Основная сессия — оркестратор: агентов можно запускать сколько угодно,
но тяжёлые команды (`go test`/`vet`/`build`, `golangci-lint`, `vitest`, `npm run check|build`,
`wails3 task`) у всех, включая саму сессию, идут через очередь `.claude/heavy.sh` — по одной
на машину, на половине ядер. Агент гоняет только свои пакеты; весь модуль, `-race
./internal/...` и базис линтера — один раз после сведения веток. Четыре параллельных полных
прогона уже клали машину пользователя намертво. Хук линтера после Edit/Write идёт через
`heavy.sh --try` и пропускается, если очередь занята.

Не делегировать: правку в один-два файла, ответ на вопрос по коду, любые операции с git,
решение об архитектуре и границах задачи, отчёт пользователю. Запуск агента стоит дороже, чем
правка в три строки.

Основная сессия делает сама: разбиение задачи и назначение файлов каждому агенту; `commit`,
`push`, ветки, разрешение конфликтов; чтение итогового дифа своими глазами; отчёт.

В задании агенту всегда три вещи: точный список файлов, которые ему можно трогать; что вернуть;
чего не делать. «Почини установку» возвращает мусор.

Параллельные агенты в одном пакете — каждый в своём worktree, и заводит его основная сессия:
`git worktree add -b <ветка> .claude/worktrees/<ветка> dev`. Опцию изоляции агента
(`isolation: worktree`) не использовать: она создаёт worktree от `main`, агент получает дерево
без последних коммитов `dev` и либо чинит не тот код, либо сам делает `reset --hard`. В задании —
путь worktree и базовый коммит, который агент сверяет первым шагом. Всё машинное (каталог с
gcc для `-race`, путь к соседнему репозиторию бэкенда) передаётся в тексте задания, а не
вписывается в `.claude/agents/*.md` и `.claude/agent-rules.md`.

Приёмка результата — по тем же правилам, что и своя работа: отчёт без вывода команд и без
`файл:строка` не принимается, «готово» без блока ПРОВЕРКИ — повод перепрогнать через
`typhon-verify`, а не поверить на слово. Находка не считается закрытой потому, что агент так
написал.

## Главный принцип

**Ошибка никогда не превращается в дефолтное значение.** Треть отчёта — это `nil`, `0`, `""`, `true`, пропущенный элемент или `Defaults()` на месте ошибки. Такой баг не ловится тестами и гарантированно ловится пользователем: антивирус держит хэндл, диск заполнен, путь длиннее MAX_PATH, нет прав на подкаталог.

Конструкции, запрещённые без исключений:

```go
if v, err := f(); err == nil { x.Field = v }          // ошибка → поле осталось нулевым
if err != nil { slog.Error(...); return nil }           // залогировал и вернул «успех»
if err != nil { return 0 } / { return true } / { return "" }
_ = filepath.WalkDir(...) / _ = os.Remove(...) / _ = f.Close()
func(_ string, d fs.DirEntry, err error) error { if err != nil { return nil } ... }
t, _, err := cl.AddTorrentSpec(spec)                    // отброшено значимое возвращаемое значение
```

Правильно: `return err`, `(T, error)`, или явный флаг `Unknown bool` в результате. Если ошибку действительно можно отбросить — однострочный комментарий «почему». `_ =` и `err == nil` без комментария не проходят ревью и ловятся `errcheck`/`nilerr` из чеклиста.

## Инварианты

### I. Хранилища (storage, settings, library, catalog, install, download, sources, updates)

1. **Одна функция атомарной записи на весь репозиторий** — `storage.WriteAtomic`. Копии `writeAtomic` в пакетах запрещены (в отчёте их было три, все без fsync). `os.WriteFile` прямо в целевой файл состояния запрещён.
2. `WriteAtomic` обязан: создать временный файл через `os.CreateTemp(dir, ...)` (не `path+".tmp"`), записать, `f.Sync()`, проверить ошибку `f.Close()`, `os.Rename`, затем fsync каталога (на Windows — best-effort с комментарием, почему). Любой из шагов пропущен — это не атомарная запись, а её имитация.
3. **Ошибка чтения ≠ пустое состояние.** `load` возвращает `(T, error)`. `fs.ErrNotExist` — единственная ошибка, которая означает «начать с пустого». Любая другая ошибка (EACCES, битый JSON, обрыв) — сервис **не стартует** (конструктор возвращает ошибку) либо переходит в read-only и **отказывается сохранять**. Проверять обе стороны: что `load` различает, И что ни один `persist` не выполнится после неудачной загрузки. В отчёте починка первой половины без второй ничего не меняет — файл всё так же затирается.
4. Обновление состояния в памяти и на диске — одна операция: изменил в памяти → `persist` → при ошибке **откатил память** и вернул ошибку. `append/delete` до `persist` с голым `return err` после — это рассинхрон, после которого следующий успешный `persist` зафиксирует испорченное состояние.
5. Ошибка `persist` всегда возвращается вызывающему и доходит до UI. `slog.Error("save ...")` + продолжение — это проглоченная ошибка (catalog.Provision, sources.settle, updates.saveManifest, install.persistLocked в отчёте).

### II. Конструкторы и пути

6. `NewService`/`NewManager` возвращают `(*T, error)`. Пустой или неразрешившийся `ConfigDir`, `GamesPath`, `InstallDir` — ошибка конструктора, `main.go` завершает запуск. Паттерн `slog.Error(...); dir = ""` запрещён: при нём `filepath.Join("", ...)` делает все пути относительными cwd лаунчера, а `persist` либо вечно падает, либо пишет «в никуда» с `nil`.
7. Запись игры с пустым `InstallDir` не принимается ни в library, ни в updates, ни в install. Любая функция, строящая путь от `InstallDir`/`Destination`, начинается с проверки на пустоту.
8. Права каталогов — режим источника, не `0o755`. umask учитывать через `os.Chmod` после создания, если нужен точный режим.

### III. Перемещение данных и откат

9. Единственная копия пользовательских данных никогда не находится в состоянии, из которого процесс не может восстановиться после аварийного завершения. Любая операция из двух и более `Rename` (`swapDirectories`, `ModeMove`+commit, patch chain) обязана иметь **восстановление на старте сервиса**: `ServiceStartup` сканирует `.partial`/`.previous`/`.staging`/`.replaced` и доводит операцию до конца или откатывает. Обработчик ошибки по месту не покрывает смерть процесса между шагами — он там просто не выполнится.
10. Перед удалением источника (`RemoveAll(src)` после copy-fallback, удаление `.previous`, удаление `.partial`) — `Sync` на каждом записанном файле и **верификация по хешу**. Сравнение размеров — не верификация; функция, которая сравнивает размеры, называется `verifySizes`, и по её результату источник не удаляется.
11. Симлинки и нерегулярные файлы: `if !d.Type().IsRegular() { return nil }` в связке с последующим удалением источника — тихая потеря данных. Симлинки копируются через `Readlink/Symlink`, остальное — ошибка.
12. `CopyDir/MoveDir/MergeDir` проверяют, что `dst` не внутри `src` и наоборот, до первого `Mkdir`.
13. `MergeDir` не удаляет целевой файл до того, как новый записан рядом и синхронизирован: пишет `target.tmp`, `Sync`, `Rename`.
14. Цепочка патчей: каждый успешно применённый патч фиксирует промежуточную версию (`registerVersion`) **до** начала следующего; прерванная цепочка не может выглядеть как доступное или применённое обновление — только как прерванная, с указанием, на каком шаге она остановилась.
15. Операции, пишущие в живую установку (in-place torrent reuse, Repair, patch chain), делают `rememberPrevious` до первого байта записи. Без резервной копии в живую установку не пишем.
16. Удаление данных загрузки (`removeContent`, `DeleteData`) вычисляет удаляемый корень из реального layout (`flat`, `inPlace`, `info.BestName()`), а не из `Destination/Name`, и отказывается удалять каталог, на который ссылается установка или идущий install-job.

### IV. Конкурентность

17. Любая проверка «занято/существует» и последующее действие — под одним захватом мьютекса. `hashBusy` → unlock → `addMetainfo` — это TOCTOU, уже уронивший активный торрент.
18. Дорогие операции (обход дерева, `stat`, опрос движка, `Inspect`) под глобальным мьютексом запрещены. Считать вне лока, под лок заносить результат.
19. Каждая горутина учтена в `wg` владельца и завершается по `ctx`. `go func(){...}()` без `wg.Add` и без `ctx` — утечка, которая может выполнить `persist`/`Drop` после `Shutdown`.
20. `context.Background()` — только в `main` и тестах. Фолбэк `if ctx == nil { ctx = context.Background() }` в сервисе запрещён.
21. Первый параметр блокирующей функции — `ctx`; длинные обходы (`WalkDir`, `DirSize`, `scanFiles`, `FindExecutables`) принимают `ctx` и проверяют `ctx.Err()`.
22. Дочерний процесс (`runner_windows`) убивается при отмене `ctx`, а не остаётся жить после `return ctx.Err()`.
23. Код с конкурентностью не считается проверенным, пока `go test -race` не прошёл на тесте, который реально создаёт конкуренцию.

### V. Ошибки и их причины

24. Разные причины — разные ошибки. «Нужен пароль», «нет тома», «CRC», «нет прав» и «формат не поддерживается» не схлопываются в один `errUnsupportedArchive`; `!ok || len(URIs) == 0` — не один `errNoTarget`; любая ошибка `downloads.Get` — не `errDownloadFailed`. Оборачивать `%w`, сравнивать `errors.Is/As`.
25. `CanAutoInstall`, `Repairable` и любой другой флаг «можно делать автоматически» выставляется **после** того, как данные для решения получены без ошибок, и никогда — безусловно.
26. Функция проверки («Verify», «verifyInstall», «StepVerify», «checkSpace») проверяет то, что написано в имени. `len(entries) == 0` — не верификация установки; `free <= 0 → nil` — не проверка места (ошибка получения свободного места = отказ, а не пропуск).
27. Структура возвращается заполненной целиком во всех ветках. Поле, заполняемое в трёх ветках из четырёх (`Plan.Candidates`, `UpdateAvailability`, `item.Destination`), — будущий сбой.
28. Одно понятие — один источник правды: список расширений архивов, нормализация версий (`VersionKey`), лимит аватара, интервал обновления — определяются в одном месте и импортируются.

### VI. Внешний мир

29. `http.Client` — всегда с таймаутом **и** с `CheckRedirect`, который повторно валидирует каждый хоп теми же правилами, что и исходный URL (схема, не-loopback, не-приватная сеть для фидов), и снимает `Authorization` при смене хоста или схемы.
30. Bearer-токен не отправляется по `http://`. Схема `TYPHON_API_URL` проверяется при старте, не-https принимается только для loopback.
31. Тело ответа — через `io.LimitReader`; `resp.StatusCode` проверяется до чтения; `defer resp.Body.Close()` на всех ветках, включая ошибочный статус.
32. Всё, что приходит извне (имена из фида, имена записей архива, пути из манифеста, `release.URIs[0]`, `opts.Type`/`InstallerPath` из UI) валидируется до использования: `..`, абсолютные пути, схема, длина, разрешённый набор значений. Имена записей архива и фидов санитизируются до показа в UI.
33. Пути исполняемых файлов (`msiexec`, установщики) — абсолютные, через `exec.LookPath` или системный каталог, не голое имя.
34. `metainfo.LoadFromFile` и любой парсинг внешнего файла — с ограничением размера.

### VII. Производительность

35. Дорогая операция выполняется один раз за вызов: `DirSize`, `Inspect`, `InspectReuse`, `dirSize` не вызываются повторно в том же потоке выполнения — результат передаётся параметром.
36. Никаких сисколлов в компараторе `sort.Slice`. Материализовать, потом сортировать.

## Что значит «исправлено»

Проверено на этом репозитории: фикс, сделанный наполовину, неотличим от отсутствующего. Перед тем как назвать находку закрытой:

- Для load/save — показать обе стороны: различение `ErrNotExist` **и** отказ от сохранения после ошибки.
- Для fsync — показать `CreateTemp`, `Sync`, проверку `Close`, `Rename`, fsync каталога, **и** что дубликаты функции удалены.
- Для отката — показать код восстановления в `ServiceStartup`, а не только обработчик ошибки.
- Для пустых путей — показать, что конструктор возвращает ошибку и `main.go` её обрабатывает, а не что «залогировано в одном из сервисов».
- Для гонок — показать тест, который падает под `-race` до фикса.
- На каждый исправленный баг — тест, который падает до фикса. Табличные, `t.TempDir()`, без `time.Sleep`. Обязательные негативные кейсы: нет файла, нет прав, битый JSON, отменённый `ctx`, частичная запись, симлинк, пустой ввод.

## Обязательный чеклист перед сдачей любой задачи

Запускать все — по одной, через очередь `bash .claude/heavy.sh <команда>` (она понимает и префиксы вида `GOOS=windows`), — и показывать вывод в ответе. **Отчитываться об успехе, не запустив команды, запрещено.** «Должно работать» и «судя по diff» — не результат. Если команда не запускается на машине (нет компилятора, нет сети) — это пишется явно, а не пропускается молча.

```bash
gofmt -l .                     # вывод должен быть пустым
go vet ./...
go build . ./internal/...
GOOS=windows go build . ./internal/...
go test ./internal/...
CGO_ENABLED=1 go test -race ./internal/...
golangci-lint run --new-from-rev=origin/dev ./...   # новый/изменённый код: 0 находок
golangci-lint run ./...                             # весь модуль: число не растёт
```

`go test -race` требует cgo и gcc (на Windows — MinGW-w64, например WinLibs из winget): его каталог добавить в `PATH` на время прогона, путь на конкретной машине в репозиторий не пишется. `zig cc` не подходит (не линкуется tsan).

`go build ./...` падает на `build/ios` (wails-скаффолд без `main`) — поэтому скоуп `. ./internal/...`; это не повод убирать команду из чеклиста.

### golangci-lint

- Версия закреплена: v2.13.1, формат конфига v2 (`version: "2"`). Конфиг — `.golangci.yml` в корне, лежит в git. Установка и запуск: `wails3 task lint:install`, `wails3 task lint`, `wails3 task lint:new REV=<rev>` (Taskfile.yml). Без бинаря команда `lint:install` ставит его через `go install ...@v2.13.1`.
- Линтеры: `errcheck` (check-blank, check-type-assertions), `govet`, `staticcheck`, `ineffassign`, `unused`, `nilerr`, `errorlint`, `contextcheck`, `bodyclose`, `gosec`, `forbidigo`, `sloglint`, форматтер `gofmt`. `nilerr` и `errcheck` — ключевые: они ловят «залогировал и вернул nil», из которого выросла треть отчёта.
- `forbidigo` делает физически невозможным: `os.WriteFile` вне `internal/storage` (инвариант 1), `context.Background/TODO` вне `main` и тестов (20), `http.Get/DefaultClient` (29), `filepath.Walk` (21), `time.Sleep` (тесты), `log.*`/`fmt.Print*` вместо slog, `os.Exit` вне main, `panic` в коде.
- `issues.max-same-issues: 0`, `max-issues-per-linter: 0` — дефолтные лимиты (3 и 50) скрывали больше половины находок. Не возвращать.
- Базис хранится в `.github/lint-baseline.txt` по ключу `GOOS` или `GOOS+теги`: набор компилируемых файлов на каждой ОС свой, поэтому и цифры свои. Проверка — `go run ./tools/lintbaseline` (`wails3 task lint:baseline`); в CI она идёт в job `lint` только при ручном запуске `ci.yml` с `full_checks=true`, на push и PR её нет. Стало меньше — понизить базис (`wails3 task lint:baseline UPDATE=true`) в том же коммите. Мерить только в чистом дереве: untracked-файлы дают другую цифру. Число может только уменьшаться. Как мерить другие ОС — скилл `lint-baseline`. История: 239 на 706f9eb до отключения G301/G306/G304, 122 на 5b22e81, 84 на v0.3.0, к 0.9 Windows и darwin дошли до нуля.
- Режим работы — `--new-from-rev`: новый и изменённый код чистый, легаси разбирается отдельными задачами.
- PostToolUse-хук в `.claude/settings.json` гоняет `golangci-lint run --fast-only ./...` после каждого Edit/Write через `heavy.sh --try` (занята очередь — пропускает); в v2 флаг `--fast-only`, `--fast` нет. Он показывает только быстрые линтеры — это не замена полного прогона из чеклиста.

Запрещено:
- `//nolint` в любом виде без однострочного обоснования, ссылающегося на конкретный инвариант выше; `//nolint` ради зелёного билда — нет.
- Править `.golangci.yml` (отключать линтеры, расширять `exclusions`, возвращать лимиты `max-*`, убирать паттерны `forbidigo`) ради прохождения.
- Помечать тесты `t.Skip`, менять их ожидания или удалять, чтобы они прошли.
- Сужать скоуп финальной проверки (`./internal/download/...` вместо `./internal/...`), чтобы не видеть чужие падения. Агент-исполнитель гоняет свои пакеты — это разделение труда, а не сужение: весь модуль после сведения веток прогоняют `typhon-verify` или основная сессия, и чужое падение там — повод разобраться, а не пропустить.

Frontend (`frontend/`): `npm run check` и `npm run build`.

### Пересборка после изменений

После чеклиста и до отчёта — пересобрать и перезапустить, не спрашивая и не дожидаясь просьбы:

```bash
bash .claude/heavy.sh wails3 task build
```

Затем прибить старый `typhon` и поднять `bin/typhon.exe` заново. Проверка живости — процесс
отвечает и в `%APPDATA%\Typhon\typhon.log` свежий хвост без паник. Если правка задевает
бэкенд (соседний репозиторий `typhon-backend`) — перезапустить и его: `go run ./cmd/api`, дождаться `GET /ready`
= 200 на `http://127.0.0.1:8080` и убедиться, что порт держит новый pid.

Живые проверки окна идут через qa-сборку (`wails3 task build:qa`: CDP на 127.0.0.1:9333,
заголовок «Typhon [qa]», с тегом `production` не собирается) и скилл `regression`. После
прогона пользователю возвращается обычная `wails3 task build`: открытый CDP-порт позволяет
любому локальному процессу управлять окном.

Изменение, не доехавшее до запущенной сборки, для пользователя выглядит как «не работает»:
он смотрит результат в реальном окне, а не в выводе тестов. В отчёте писать pid и результат
проверки.

Перед commit/push: `git status` не тянет бинарники, `bindings/`, `dist/`

## macOS

Всё про работу на маке — `devmock`, CrossOver и `internal/wine`, связка ключей, трей, маковский
чеклист и релиз бандла — в скилле `macos`; он подгружается, когда задача касается мака. Отсюда
остаются правила, которые действуют и при разработке на Windows:

- Моки — только в `*_devmock.go` с `//go:build devmock && !windows`; в exe для пользователя они
  не попадают (`internal/devmock/forbid_devmock.go` не компилируется под `windows` и
  `production`). Тесты, проверяющие только Windows (буквы дисков, реестр, COM), живут в
  `*_windows_test.go`; остальные обязаны быть зелёными на macOS без `t.Skip`.
- `internal/wine` — единственное место, знающее про CrossOver, и не импортирует `platform`,
  `install`, `library`, `procs`.
- Подготовка окружения игры — подменяемое поле сервиса (`install.Service.prepareRuntime`,
  `library.Service.prepare`). Любой новый тестовый конструктор обязан её заглушить: иначе тесты
  на маке заводят настоящие бутыли CrossOver (однажды — 29 штук на 12 ГБ).
